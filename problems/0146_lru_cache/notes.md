# 146. LRU Cache

- 链接: https://leetcode.com/problems/lru-cache/
- 难度: Medium
- 最优解:

## 题型
设计 · 哈希表 · 链表

## 识别信号
- get 和 put 都要求 O(1) 平均时间
- 容量满时要淘汰"最久未使用"的键，而每次 get 或 put 都会改变使用顺序

## 解题步骤
记 c = capacity，m = 调用次数。
1. 暴力：字典存键值，另用一个列表记录使用顺序；每次访问把键从列表中删掉再追加到末尾，满了就删列表开头，单次 O(c)，总 O(m·c)
2. 瓶颈：在顺序列表里按键查找并删除要 O(c)
3. 优化：用双向链表维护使用顺序（一端最新、另一端最旧），哈希表存 键 → 链表节点；定位节点 O(1)，从链表中摘下并移到最新端也是 O(1)；满了就删最旧端的节点，并用节点里存的键删除哈希表条目。单次 O(1)，空间 O(c)
4. Python 里 collections.OrderedDict 的 move_to_end 和 popitem(last=False) 就是同一种结构，可以直接用

## 关键一步
哈希表直接定位到双向链表里的节点，双向链表让任意节点 O(1) 摘下并移到最新端，两者结合才能让 get 和 put 都是 O(1)。

## 易错点
- get 命中时也要把该键移到最新端，不只是 put
- put 已存在的键：更新值并移到最新端，不触发淘汰
- 淘汰最旧节点时要同时删除哈希表里的键，所以链表节点里要存 key
- 头尾各放一个哨兵节点，插入和删除时就不用特判空链表或首尾节点
- 值可以是 0，判断是否命中要用 key in 字典，不能看取出的值真假
